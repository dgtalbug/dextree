Dextree

Index your codebase into a navigable semantic graph - inside VS Code.

"Human-first visual exploration of code, inside the IDE, with the same indexed graph durably exportable to Mermaid, Canvas, PNG/PDF, and embeddable web components - enriched with diagnostics, git history, and test linkage that competitors can't access because they live outside the editor."

The graph is the product. Visualizations, exports, MCP, and Alfred are surfaces over the same indexed substrate.

What it is

The 5-second pitch

01 / Index once

One graph, not a pile of feature silos

Dextree indexes a codebase into a semantic graph, then treats that graph as the product. Files, symbols, calls, imports, annotations, tests, and quality signals all land in the same substrate.

02 / Query everywhere

Every surface reads the same DuckDB graph

The in-IDE webview is primary, but tree view, MCP, CLI, exports, and the Vite component are just different lenses over the same indexed store.

03 / Export anywhere

Mermaid first, then Canvas, PNG, PDF, SVG, MCP, Alfred

The expensive part is indexing. Rendering is surface area: Mermaid diagrams, Obsidian Canvas, raster and vector exports, agent access, and narrative reports all derive from the same graph.

Why it is different

The moat is not "graph DB." The moat is VS Code.

Competitors converge on Tree-sitter plus a headless database plus MCP. Dextree chooses the open angle: stay inside the editor, fuse the graph with what the editor already knows, and make that graph exportable instead of disposable.

Direct from the strategy doc: being inside VS Code makes LSP truth, diagnostics, git blame, and test discovery available to the same graph competitors query without those signals.

Headless tools see

  • syntax trees and repository text
  • static imports and heuristics
  • MCP as the primary surface
  • no access to live editor state

Dextree sees

  • LSP symbols, references, calls, hover, and type hierarchy
  • live diagnostics from installed linters and TS server
  • git blame, recency, diff-to-symbol mapping, blast radius
  • test discovery and export surfaces from the same graph

High-level design

Six layers, one graph contract

1

Parsing

Tree-sitter WASM parses workspace files immediately so the graph is useful before semantics arrive.

2

Extraction

Pass 1 extracts files, symbols, and naive edges. Pass 2 enriches the same schema via LSP or compiler APIs.

3

Storage

DuckDB plus DuckPGQ hold the graph; vss and fts stay opt-in on the same file.

4

Query

Traversal, PageRank, symbol lookup, subgraph extraction, blast radius, and filters all sit behind one query layer.

5

Presentation

Sigma webview, tree view, exporters, settings UI, and the Vite component are different renderers over shared data.

6

Integration

MCP, CLI, and Alfred expose the same graph outside the primary in-IDE experience.

Two-pass architecture

Pass 1 / Pass 2

state

Pass 1 makes the graph visible fast. Pass 2 upgrades the same schema in place: resolved call edges, signatures, diagnostics, framework annotations, and test linkage.

Alfred

          
Opt-in narrative layer. BYOK. Editable prompt files.

        

        

          

            

              Alfred stays off by default. First use is gated, preview-first, and cost-aware.
              Providers are BYOK: Anthropic, OpenAI, Ollama, and eventually VS Code LM when stable.
            

            

              The prompt system is plain markdown with YAML frontmatter, declared queries, and
              template variables from
              inputs.*, graph.*, and
              ctx.*. The repo ships the prompt library in
              .dextree/alfred/, and Alfred discovers prompts at startup.
            

            

              Design-doc language calls the grammar Handlebars; the prompt README documents a
              Mustache subset. The important part is the same: prompts stay user-readable,
              user-editable, and query-declared.

How it is being built

          
Agentic, but with clean boundaries.

        

        

          

            
Mode A / default

            
Local Claude Code Workspace

            

              The day-to-day path: local Claude Code on the laptop, rich multi-sub-agent flow (Plan,
              Explore, Implementer, Tester, Reviewer, Pusher), isolated worktrees, then a draft PR
              to GitHub.
            

          

          

            
Mode B / fallback

            
Cloud Claude via GitHub Action

            

              The phone-controlled path: comment @claude implement on
              GitHub, let the Action run a single Claude session in the cloud, then hand off the PR
              to the same CI and Copilot review pipeline.
            

          

        

        

          The handoff boundary is the PR. Claude builds. GitHub Actions checks. Copilot handles
          review, docs, release notes.
